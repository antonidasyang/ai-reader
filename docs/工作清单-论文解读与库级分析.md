## 1. 三个贯穿全局的设计决定

**决定 A:论文事实包(digest)是全系统的货币单位。**
§2 快速解读的产出是**结构化 JSON digest(1~2k token)**,不是 Markdown。§8~§15 全部库级分析**只读 digest,绝不读全文**。
理由:30 篇论文全文单次约 40 万 token,不可行;50 份 digest ≈ 75k token,一次调用装得下(`Settings::contextWindow` 默认 128000)。
推论:**没有快速解读就没有库级分析**——M1 是 M4~M7 的硬前置,批量(M2)是让库级分析有料可读的前提。

**决定 B:模型输出结构化 JSON,Markdown 由客户端渲染。**
§4.3(区分作者主张 / 实验证据 / AI 评议 / 推测)、§5(只重生成某一部分)、§10(比较表)、§16(导出)这四条需求**无法在自由 Markdown 上事后实现**,必须一开始就结构化。
每条结论统一形状:`{text, source: author_claim|experimental|ai_analysis|speculation, evidence:[{blockId, quote}]}`。
`LlmClient` 没有 JSON mode,但有 tools(`ToolDef.inputSchema`):用**强制单次工具调用**拿结构化输出;失败降级链 = ① 从正文里抠 JSON → ② 加严提示重试一次 → ③ 报「分析失败」并留失败原因(§17)。

**决定 C:§4.4「不得伪造页码」靠校验器,不靠 prompt。**
喂全文时每段带 `[b<id> p<page>]` 标记,要求模型引用 `blockId`;拿回结果后把 `quote` 与该 block 原文做**归一化 + 模糊匹配**;对不上的证据标记为「未证实」,并把该条结论从「作者主张 / 实验证据」**降级为「AI 分析(无证据支撑)」**。
校验器是 M0 的组件,不是 M1 的收尾工作(见 R2)。

## 2. 数据模型(全部走现有通用同步底座,服务端零改动)

```
project_profile    id = uuidv5(ns, projectId + "|profile")                  课题共享一份
  data: { goal, questions[], scenarios, hypotheses[], scope, outOfScope,
          dimensions[], stage, background }                                  // §6

paper_analysis     id = uuidv5(ns, projectId|paperId|kind|authorId)         每人一份
  kind: quick | deep                                                         // §2 / §3
  data: { status, model, inputHash, digest{...}, modules{...}, updatedAt }
  // quick 的 digest 直接内联(约 5KB);deep 的载荷走 zlib+base64(PayloadCodec)

library_analysis   id = uuidv5(ns, projectId|kind[|scopeHash])              课题共享一份
  kind: taxonomy | map | consensus | evolution | coverage
        | opportunities | actions | compare                                  // §8~§15
  data: { current: {payload, generatedBy, generatedAt, model}, history:[最近3版,压缩] }
  // compare 按所选论文集合的 scopeHash 分键,互不覆盖

analysis_note      id = uuidv5(ns, projectId|paperId|authorId)              每人一份
  data: { notes:[{anchor, body, createdAt}], edits:{moduleId: 用户改写} }    // §5 §16
```

- **归属模型**沿用 `AiArtifactService`:`paper_analysis` / `analysis_note` 按 author 分键(每人一份);`library_analysis` / `project_profile` 不含 authorId(课题共享,决策 3)。
- **`inputHash`** = hash(blocks + prompt 版本 + profile + model),用于 §17「分析结果可能过期」——档案改了、换模型了、重新分段了,读出来即判过期。
- **载荷压缩**沿用 `PaperSyncService.cpp` 里现成的 `encodePayload`/`decodePayload`(zlib + base64)。
- **同步量**:digest 约 5KB/篇,100 篇 500KB,远低于服务端 32MB 的 `BODY_LIMIT`。

## 8. 风险 / 须正视

- **R1(高)模型能力**:本地网关的 Qwen3.8-27B 大概率撑不住 §3.6 批判性分析与 §11 共识冲突判定 → **必须能按功能选模型**(M0.7)+ 一套人工评测集(§9)。
- **R2(高)证据幻觉**:校验器(M0.4)是**必须先写**的组件,不能后补;先出 UI 再补校验等于把 §4.4 交给运气。
- **R3(中)离屏批量的 CPU / 网络**:100 篇 × 分段(PDFium 全局锁)+ GROBID 往返 → 限流、可暂停、可断点续跑(M2.3)。
- **R4(中)token 成本**:一篇 10 页论文约 8~15k token;快速解读 1 次调用、深度精读 9 次;100 篇批量约 120 万 token 输入 → digest 按 `(paperId, model, promptHash, profileHash)` 缓存,并复用协作者已生成的 digest(5 人组只付 1 份)。
- **R5(中)UI 面积**:5 个新 QML,而 `Main.qml` 已 1694 行 → M0 先拆面板注册。
- **R6(低)同步载荷**:digest 约 5KB/篇,100 篇 500KB,远低于服务端 32MB 的 `BODY_LIMIT`,安全。

## 10. 排期建议

```
M0 地基(编解码/结构化输出/证据校验/存储/研究档案/按功能配模型)
 └─ M1 单篇快速解读(digest = 全系统货币)
     └─ M2 离屏批量(PaperSource + 队列)  ← 库级分析的燃料
         ├─ M3 深度精读 + 精读交互
         ├─ M4 归类 + 比较
         │    └─ M5 结果管理与导出
         └─ M6(P1)地图 / 共识冲突 / 演进 / 覆盖 / 复现辅助
              └─ M7(P2)候选研究机会 / 行动建议
横切 X.1 状态机自 M1 起贯穿;X.2 缓存复用自 M2 起;§9 评测集在 M1 完成时就要建。
(spike)PDF 证据高亮叠加层:与主线并行,不阻塞任何里程碑。
```

理由:决定 A 让依赖关系变成一条直线——**digest 没跑通,库级分析全是空中楼阁**;M3 精读虽是 P0,但它只服务单篇,让位给「批量出 digest」是决策 1 的用意。M4/M5 与 M6/M7 之间只隔一层数据依赖,可按人手并行。
